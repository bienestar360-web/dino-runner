El stack técnico de Dino Runner: Phaser, Vercel y Supabase

Dino Runner usa tres tecnologías principales: Phaser para el motor del juego, Vercel para el hosting estático y Supabase para el ranking global. No hay backend propio, no hay base de datos local, no hay proceso de build. Esta guía explica cada pieza, por qué se eligió y qué alternativas se descartaron.

Phaser 3.80: el motor del juego

Phaser es un framework de JavaScript para juegos 2D en navegador. Dino Runner usa Phaser 3.80 por tres razones:

1. Es maduro. Phaser lleva más de una década en desarrollo. Tiene documentación extensa, comunidad activa y ejemplos para casi cualquier mecánica.

2. Es ligero. El build de producción de Phaser pesa alrededor de 1 MB. Para un juego de scroll lateral, es más que suficiente.

3. Es gratuito. Phaser es open source (MIT). No hay licencias, no hay costes por uso.

Lo que Phaser no hace: no genera gráficos, no compone música, no gestiona el ranking. Dino Runner usa sprites procedurales (generados en código) y el ranking se gestiona con Supabase.

Alternativas descartadas: Unity WebGL (demasiado pesado para un juego de navegador), PixiJS (más bajo nivel, requiere más código), canvas puro (reinventar la rueda).

Vercel: el hosting estático

Vercel aloja el sitio como archivos estáticos. No hay servidor dinámico: el juego se sirve como HTML, CSS y JavaScript. Esto tiene tres ventajas:

1. Velocidad. Los archivos estáticos se sirven desde CDN, con latencia mínima.

2. Simplicidad. No hay que configurar servidores, ni balanceadores, ni bases de datos.

3. Despliegue automático. Cada push a GitHub despliega en producción en ~30 segundos.

Lo que Vercel no hace: no ejecuta código de servidor (a menos que uses funciones serverless, que Dino Runner no usa). El ranking se gestiona directamente desde el navegador con Supabase.

Alternativas descartadas: Netlify (similar, pero Vercel ya estaba configurado), GitHub Pages (sin despliegue automático desde el repo), servidor propio (complejidad innecesaria).

Supabase: el ranking global

Supabase es un backend-as-a-service basado en PostgreSQL. Dino Runner lo usa solo para el ranking: guardar el top 3 global, leerlo en el Game Over y actualizarlo cuando una partida entra en el corte.

La tabla del ranking tiene tres columnas: alias, score y timestamp. No hay usuarios, no hay autenticación, no hay datos personales. El alias se guarda en el navegador del jugador y se envía a Supabase al morir.

Lo que Supabase no hace en Dino Runner: no gestiona cuentas, no guarda partidas, no envía emails. Es solo una tabla de 3 filas.

Alternativas descartadas: Firebase (más caro a escala, más complejo de configurar), backend propio con Node.js (complejidad innecesaria para 3 filas), localStorage (no es global, no compite entre jugadores).

Lo que no hay en el stack

Dino Runner no tiene:

  • Backend propio. No hay Express, no hay Django, no hay Rails.
  • Base de datos local. No hay SQLite, no hay IndexedDB para el ranking.
  • Proceso de build. No hay Webpack, no hay Vite, no hay Babel. Los archivos se sirven tal cual.
  • Sistema de autenticación. No hay login, no hay OAuth, no hay JWT.
  • CDN propio. Vercel incluye CDN en el hosting estático.

Esa ausencia es deliberada. Cada pieza que no está es una pieza que no hay que mantener.

Cómo se comunican las piezas

El flujo es simple:

1. El jugador abre `mydinorun.com`.

2. Vercel sirve `index.html`, `game.js`, `style.css` y `supabase.js`.

3. Phaser arranca el juego en el navegador.

4. Al morir, `supabase.js` envía el score a Supabase.

5. Supabase compara con el top 3 y actualiza si corresponde.

6. La pantalla de Game Over muestra el top 3 actualizado.

No hay llamadas al servidor propias. Todo el tráfico es: navegador → Vercel (estático) y navegador → Supabase (API REST).

Por qué este stack y no otro

La decisión se resume en una frase: mínimo mantenimiento, máxima velocidad. Un juego de navegador no necesita un backend complejo. Un ranking de 3 filas no necesita una base de datos dedicada. Un sitio estático no necesita un servidor.

Ese minimalismo tiene un coste: si Supabase cae, el ranking no funciona. Si Vercel cae, el juego no carga. Pero ambos servicios tienen SLA altos y el juego no es crítico.
